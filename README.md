## 1. 项目简介

本项目使用 Linux Socket、`epoll` 与线程池实现多客户端 TCP 消息服务器。主线程通过 `epoll_wait()` 管理连接与事件，工作线程负责非阻塞接收、应用层消息解码、回显和发送。使用 **4 字节长度头 + 消息体** 解决 TCP 字节流的消息边界问题。

近期完成了 **Connection 连接管理重构**：不再仅用可能重复分配的 fd 来代表客户端，而是为每个连接分配独立 ID，通过智能指针持有连接对象，并将收发缓冲区移入各自的 Connection，以减少共享状态和全局锁竞争。

当前是可运行、已进行阶段性压力测试的学习项目；不宣称已具备生产环境网络库的完整能力。

## 2. 已实现功能

- 使用 `socket()`、`bind()`、`listen()`、`accept()` 实现 TCP 连接建立。
- 使用 `epoll_create1()`、`epoll_ctl()`、`epoll_wait()` 管理监听与客户端事件。
- 使用线程池异步处理客户端事件，结合 `EPOLLONESHOT` 和 `EPOLL_CTL_MOD` 重新激活事件。
- 客户端 Socket 设为非阻塞模式；处理 `EINTR`、`EAGAIN`、`EWOULDBLOCK`。
- 接收数据采用连接级缓冲区，按 Header + Body 循环解码，支持粘包与拆包。
- 发送数据采用连接级缓冲区，支持部分发送；存在待发送数据时注册 `EPOLLOUT`。
- 使用 `MSG_NOSIGNAL` 处理发送时的 SIGPIPE 风险。
- 引入 Connection 唯一 ID、`shared_ptr`、`closing` 原子状态和连接级互斥锁。
- 使用 Python 测试脚本验证回显、分包、粘包、32KB 消息、异常断连和非法长度包。

## 3. 核心架构

```text
客户端
  |
  v
TCP / Linux Socket
  |
  v
epoll_wait() 主事件循环
  |-- id = 0 -----------> acceptClient() -> 创建 Connection -> 注册 epoll
  |
  `-- id > 0 -----------> m_connections.find(id)
                                  |
                                  v
                           shared_ptr<connection>
                                  |
                                  v
                             线程池任务
                                  |
                            conn->ioMutex
                                  |
                             handClient()
                            /           \
                     handleRead()    handleWrite()
                          |              |
                  m_recvBuffer       m_pending
                          |              |
                    Message::decode  send / EPOLLOUT
                            \           /
                             rearmClient()
                                  |
                       必要时 closeClient()
```

线程池的具体工作线程数量由 `ThreadPool` 实现与配置决定；压测中的“100 并发线程”指 **Python 客户端的测试线程**，不是服务器工作线程数量。

## 4. Connection 连接管理重构

### 4.1 为什么要引入 Connection？

Linux 文件描述符可以复用：客户端 A 的 fd 关闭后，客户端 B 可能获得同一个编号。如果服务器旧任务仅凭 fd 操作 Socket 或缓冲区，就存在误操作新连接的风险。

现在通过独立 ID 表示连接身份，fd 只用于操作 Socket。

```cpp
struct connection
{
    int fd = -1;
    uint64_t id = 0;
    std::atomic<bool> closing{false};

    std::string m_recvBuffer; // 当前连接的接收缓冲区
    std::string m_pending;    // 当前连接的待发送缓冲区

    std::mutex ioMutex;       // 当前连接的处理流程同步
};
```

服务器维护连接表：

```cpp
std::unordered_map<uint64_t, std::shared_ptr<connection>> m_connections;
std::mutex m_connectionsMutex;
std::atomic<uint64_t> m_nextConnectionId{1};
```

### 4.2 生命周期

1. **建立连接**：`accept()` 返回 `cfd`，为其设置非阻塞；`fetch_add(1)` 分配唯一 ID。
2. **保存记录**：创建 `shared_ptr<connection>`，插入 `m_connections`；普通连接的 `epoll_event.data.u64` 保存连接 ID，监听事件约定 ID 为 `0`。
3. **分发任务**：主线程根据 ID 查找 Connection，线程池任务捕获 `shared_ptr`，避免对象提前析构。
4. **处理读写**：工作任务先获取该连接的 `ioMutex`，再调用 `handClient()`、`handleRead()`、`handleWrite()` 和 `rearmClient()`。同一连接的操作串行，不同连接可并行。
5. **关闭连接**：使用 `closing.exchange(true)` 避免重复发起关闭；清理缓冲区和连接表记录，取消 epoll 注册并关闭 fd。

`shared_ptr` **保证对象生命周期**，但不自动保证 Socket fd 的生命周期。当前实现依赖收发与关闭遵守同一连接级同步约定，尚未验证所有可能的竞态场景。

### 4.3 重构前后对比

| 项目 | 重构前 | 重构后 |
|---|---|---|
| 连接标识 | 主要使用 fd | 唯一 `uint64_t` ID |
| 连接存储 | 分散记录 | `shared_ptr<connection>` |
| 接收缓冲区 | `unordered_map<int, string>` | `conn->m_recvBuffer` |
| 发送缓冲区 | `unordered_map<int, string>` | `conn->m_pending` |
| 缓冲区同步 | 两把全局互斥锁 | 每个 Connection 自己的 `ioMutex` |
| 连接表同步 | `m_connectionsMutex` | 仍然保留 |

设计收益主要是 **连接状态隔离、减少全局锁、减少按 fd 查 Map、简化资源管理**。在目前的短连接压测中，尚未证明吞吐性能显著提升。

## 5. 通信协议

采用 **4 字节固定长度头 + N 字节消息体**：

```text
+---------------------------+---------------------------+
| Header：4 字节 uint32_t   | Body：N 字节              |
| 网络字节序，记录 Body 长度 | 消息正文                  |
+---------------------------+---------------------------+
```

最大 Body 长度为 **65536 字节（64 KiB）**。例如发送 `Hello`：

```text
00 00 00 05  48 65 6c 6c 6f
长度 = 5     H  e  l  l  o
```

- 编码使用 `htonl()`，将长度头与正文拼接。
- 解码使用 `ntohl()`，检查长度合法性和包是否完整。
- `Complete`：取出一条完整消息并从缓冲区消费相应字节。
- `Incomplete`：保留数据等待后续 `recv()`。
- `Invalid`：发现非法长度，进入关闭处理。

由于服务器要求自定义长度协议，直接运行 `nc 127.0.0.1 9999` 并输入普通字符串，不能得到正常回显。应使用按协议封包的客户端，例如项目中的 Python 测试脚本。

## 8. 关键问题与排查记录

1. **fd 事件重复投递**：使用 `EPOLLONESHOT` 控制事件投递，并在处理完毕后重新激活。
2. **非阻塞收发**：区分 `EINTR` 与 `EAGAIN/EWOULDBLOCK`，发送成功多少字节就从缓冲区移除多少。
3. **TCP 粘包拆包**：按每个连接维护接收缓冲区，循环解析 Header + Body。
4. **fd 复用风险**：引入独立连接 ID、`shared_ptr` 和连接级同步，降低旧任务误操作新连接的风险。
5. **重复加锁死锁**：线程池入口已经持有 `conn->ioMutex`，内部函数不能再次锁定同一把普通 `std::mutex`。
6. **缓冲区误复制**：`auto data = conn->m_pending` 得到字符串副本，发送时要使用 `std::string& data = conn->m_pending` 修改原缓冲区。
7. **epoll 事件数据混用**：客户端重新注册事件时必须使用 `ev.data.u64 = conn->id`，不能继续用 `ev.data.fd = fd`。
8. **性能测试被日志拖慢**：大量终端输出可能严重影响工作线程调度与测试耗时，采用重定向进行对照验证。

## 10. 项目讲解要点

**为什么不用 fd 直接表示客户端？**  
fd 可以复用，不能充当永久不变的连接身份；Connection ID 用于识别连接，fd 只用于系统调用。

**为什么要使用 `shared_ptr`？**  
线程池任务捕获连接对象，避免对象被连接表删除后立即析构。但 `shared_ptr` 不能代替 fd 的关闭同步。

**`EPOLLONESHOT` 和 `ioMutex` 有什么不同？**  
`EPOLLONESHOT` 控制 epoll 事件重新激活的时机，`ioMutex` 协调同一 Connection 的任务对内部状态的访问。

**如何解决 TCP 粘包拆包？**  
固定 4 字节长度头表明 Body 长度，按连接累计收到的字节，足够一个包才解码，否则等待下次读取。

**如何处理部分发送？**  
使用 `send()` 的实际返回值删除已发送部分，保留剩余字节，必要时关注 `EPOLLOUT` 后继续发送。

**测试数据证明了什么？**  
本机 100 个 Python 测试线程、累计 30 万次短连接操作，正常回显验证 17.4 万次通过、客户端失败 0；该结果不等于 30 万同时在线连接，也不能保证所有线程竞态和内存问题都已被排除。
